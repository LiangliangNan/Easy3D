    - [x] IMPOSSIBLE (2026-11-14, decided from the code rather than from preference): with Vulkan, `Drawable::buffer_stats(std::ostream &output)` cannot report the number of buffers and their total size. The original question was which of two options is better; neither delivers the figure.
      - Why the information is not reachable: under Vulkan a drawable holds no buffers at all. `easy3d/renderer/backends/vulkan/drawable.h` declares only `class DrawableRenderer` with an opaque `struct Impl`, and the allocation happens inside the implementation translation unit, where `VkBufferCreateInfo::size` is set and then not retained per drawable (`easy3d/renderer/backends/vulkan/render_device.cpp:499-513`). Buffers are also not one per drawable: a point drawable binds two (`points->buffer` and `geometry->buffer`, ibid. `:3466-3471`), the picking pass reuses the same geometry through different descriptor sets, and the shared caches grow their own allocations (`DrawBufferCache`, ibid. `:4074`). So "the number of buffers and their total size" is not a property a `Drawable` has — it is a property of the backend's allocation strategy, which changes with the device features (see the expanded-point fallback in `changes/vulkan.md`).
      - Option 1 (a new backend query) rejected: it means storing every allocation size, adding a per-drawable total to the GPU cache, and widening the backend-neutral `RenderDevice` interface with an accessor whose only consumer is a diagnostic print. The Vulkan-internal classes cannot be reached from `Drawable` otherwise, so this is new public contract surface for a debug output line — and the number it returns is still cache policy, not a drawable attribute, so it would need documenting as that.
      - Option 2 (counters in `Drawable`) rejected as wrong rather than merely duplicative: today `buffer_stats()` multiplies CPU element counts by `sizeof` (`easy3d/renderer/drawable.cpp:109-130`), which under Vulkan is not what the GPU holds — the fallback point path allocates four vertices plus indices per point, so a Drawable-side total would understate that drawable by a factor depending on whether `largePoints` is enabled. It also cannot see the second buffer of a point drawable. That is the same failure mode as the legacy positional `Viewer` constructor: an interface that compiles and reports a confident, wrong number.
      - What is actually true of both backends: the existing OpenGL numbers are the CPU-side formula, so `buffer_stats()` already reports the same bytes in both backends for the geometry it can see. Making it "report the number of buffers and their total size" under Vulkan would therefore either require the new API of Option 1 or produce the misleading figures of Option 2; leaving it as the geometry-formula it is, keeps the numbers honest in both backends. Nothing is hidden from `Drawable` that it could legitimately print.
      - Follow-up if a real GPU-memory report is ever wanted: build it as a device-level diagnostic (`VulkanDevice` allocation totals plus, on OpenGL, `GL_BUFFER_SIZE` queries), not as a per-drawable statistic.
